# Plan: Structured reporting workflow (blueprint + notes.md)

## Context

`webmd/note-to-local.md` (current revision) defines a three-part reporting workflow for `LeanForControl`:

1. **Automated blueprint** — `LeanArchitect` (Lean dependency) extracts blueprint data from `@[blueprint]`-annotated Lean declarations; `leanblueprint` (Python plasTeX plugin) renders that into HTML/PDF.
2. **Hand-edited `notes.md`** at the project root — sprint progress notes; updated each session.
3. **End-of-session workflow** — make Lean compile → update `notes.md` → regenerate blueprint.

Repo state today (verified): `notes.md` does not exist; no `blueprint/` directory; no `LeanArchitect` dependency in `lakefile.toml`; no blueprint/plastex config; no `@[blueprint]` annotations in any Lean file. `.github/workflows/lean_action_ci.yml` already runs `lean-action` and `docgen-action`, but does **not** build the blueprint. GitHub remote is `AnandGokhale/LeanForControl`.

User-chosen scope:

- Annotate **only the LinearSystems track** in this first pass: `observabilityMatrix`, `IsObservable`, `observabilityMatrix_apply`, `observabilityMatrix_mulVec_apply`, `isObservable_iff_observabilityMatrix_ker_trivial` (Observability.lean), `controllabilityMatrix`, `controllabilityMatrix_apply` (Controllability.lean).
- **Local-only, manual** build pipeline. No new CI workflows.
- System deps (`graphviz`, `libgraphviz-dev`) and Python `leanblueprint` are **already installed** by the user; `leanblueprint` lives in conda env `cortese`. Any *other* packages must be confirmed before install.
- Blueprint scaffold is bootstrapped by **the user running `leanblueprint new` interactively**; we then customize the generated files.

External-tool references:

- `LeanArchitect` — <https://github.com/hanwenzhu/LeanArchitect>. Added via `[[require]]` in `lakefile.toml`. Annotation form: `@[blueprint "thm:foo"]` (with optional `statement`, `proof`, `uses`, `proofUses` fields). Extraction: `lake build :blueprint`. Output: LaTeX nodes under `.lake/build/blueprint/`.
- `leanblueprint` — <https://github.com/PatrickMassot/leanblueprint>. Bootstrap: `leanblueprint new`. Build: `leanblueprint web`, `leanblueprint pdf`, `leanblueprint all`. Verification: `leanblueprint checkdecls`. Local serve: `leanblueprint serve`.

Each step ends with the relevant build/check command green before moving on.

Append the `[[require]]` block. Run `lake update LeanArchitect` followed by `lake build`. Confirm:
- `lake-manifest.json` now has a `LeanArchitect` entry;
- `lake build` is green for the existing project.

### Step 3 — Bootstrap the blueprint scaffold (user-run, interactive)

Tell the user to run, in a terminal at the project root:

```

```

…and answer its prompts (project name, GitHub URL `https://github.com/AnandGokhale/LeanForControl`, author, etc.).

After they confirm completion, inspect `blueprint/`. Expected layout:
- `blueprint/src/web.tex`, `print.tex`, `content.tex`
- `blueprint/src/macros/{common,web,print}.tex`
- `blueprint/lean_decls` (declaration-name list maintained by `checkdecls`)

### Step 4 — Annotate LinearSystems declarations

For each of the seven declarations, add an `@[blueprint "<label>"]` attribute. Suggested labels (mirror typical mathlib/blueprint conventions, kept short):

| Declaration | Label |
| --- | --- |
| `LinearSystems.observabilityMatrix` | `def:observabilityMatrix` |
| `LinearSystems.IsObservable` | `def:isObservable` |
| `LinearSystems.observabilityMatrix_apply` | `lem:observabilityMatrix-apply` |
| `LinearSystems.observabilityMatrix_mulVec_apply` | `lem:observabilityMatrix-mulVec-apply` |
| `LinearSystems.isObservable_iff_observabilityMatrix_ker_trivial` | `thm:isObservable-iff-ker-trivial` |
| `LinearSystems.controllabilityMatrix` | `def:controllabilityMatrix` |
| `LinearSystems.controllabilityMatrix_apply` | `lem:controllabilityMatrix-apply` |

For the milestone theorem, also fill in `uses := [..]` listing the two definitions and the bridge lemma so the dep graph is non-trivial.

Add `import LeanArchitect` at the top of both files. Run `lake build`; confirm no regression.

### Step 5 — Wire annotated nodes into `content.tex`

Replace the boilerplate body of `blueprint/src/content.tex` with one chapter `Linear systems` containing one section `Observability and controllability matrices`. Inside, write `\begin{definition}\label{def:observabilityMatrix} … \inputleannode{def:observabilityMatrix} \end{definition}` for each label, and a `\begin{theorem}\label{thm:…}\uses{def:observabilityMatrix, def:isObservable, lem:observabilityMatrix-mulVec-apply}\inputleannode{thm:isObservable-iff-ker-trivial}\end{theorem}` block.

Add the LaTeX include `\input{../../.lake/build/blueprint/library/LeanForControl}` (path adjusted once we see what `lake build :blueprint` actually emits — likely under a sub-namespace tree) at the appropriate point in `content.tex`, per the LeanArchitect README's `\inputleannode` example.

### Step 6 — Smoke test the pipeline

Run, end to end:

```
lake build                                  # project still compiles
lake build :blueprint                       # extracts blueprint LaTeX nodes
conda activate cortese
leanblueprint checkdecls                    # all labels resolve to real decls
leanblueprint web                           # renders blueprint/web/
leanblueprint serve                         # spot-check at http://localhost:8000
```

Expected outcomes:
- `.lake/build/blueprint/` populated with LaTeX nodes for the seven labels.
- `checkdecls` reports zero missing declarations.
- `blueprint/web/index.html` renders the chapter and the dependency graph between the seven nodes.

If `checkdecls` fails on a label mismatch, prefer fixing the LaTeX label to match the Lean attribute's string (single source of truth: the `@[blueprint "..."]` argument).
